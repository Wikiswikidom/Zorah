# Phase 2D-10 — Audit Trail

## Status
Implementation complete; production browser/build verification remains a deployment gate.

## Implemented
- `admin_audit_logs` append-oriented audit table.
- Database trigger coverage for products, variants, collections, collection membership, inventory movements, landing sections, campaigns, campaign targets, journal articles and merchandising.
- Actor UUID and actor role capture where the request is authenticated.
- Action classification for insert/update/delete plus publish, unpublish, schedule, pause and archive transitions.
- Before/after JSON metadata for traceability.
- Timestamped records using database `now()`.
- RLS enabled; audit records are readable only by Super Admins.
- Client roles cannot write arbitrary audit records; audit writes are generated by trusted database triggers.
- Passwords, authentication secrets and payment credentials are not stored in audit metadata.
- `/admin/audit` workspace is restricted to Super Admin.

## Security acceptance tests
1. Customer cannot read audit logs.
2. Non-Super-Admin staff cannot read audit logs.
3. Client cannot insert/update/delete audit records directly.
4. Admin mutations create an audit event.
5. Publication changes are classified correctly.
6. Join-table mutations do not crash the trigger even when no single UUID `id` exists.
7. Audit records contain no authentication/payment secrets.
8. Audit access is server-role-gated as well as database-RLS protected.
